# Перенос стенда на отдельную машину

Инструкция для организатора. Описывает полный путь: упаковать стенд на рабочей машине, перенести одним файлом, распаковать на машине с ускорителем и открыть ноутбук в браузере.

Целевая машина в примерах: `192.168.52.118`, пользователь `dmd`.

Порядок рассчитан на то, что участник ничего не устанавливает. Всё окружение собирается один раз организатором и живёт в контейнере.

---

## Что переносится

Замерено на текущем составе стенда.

| Часть | Вес | Зачем |
| --- | --- | --- |
| Веса моделей, папка `models` | 3 707 МБ | распознавание, глубина, сравнение изображений |
| Набор данных, папка `data` | 600 МБ | кадры пяти камер, разметка, измерения дальномера |
| Ноутбук и готовые ролики | 6 МБ | занятие целиком |
| Код, документы, описание контейнера | менее 1 МБ | вспомогательные модули и порядок запуска |
| Архив целиком | 4,21 ГБ | |

В архив не попадают история изменений, локальное окружение Windows и кеши. Локальное окружение бесполезно на целевой машине: в нём 5,2 ГБ библиотек, собранных под Windows.

Образ контейнера в архив тоже не попадает. Он собирается на целевой машине по описанию из папки `docker`. Это требует выхода в интернет. Собранный образ весит 17,8 ГБ, замерено сборкой на рабочей машине, и почти весь объём приходится на библиотеки расчётов на ускорителе. Сборка занимает около четверти часа. Если интернета на целевой машине нет, смотрите раздел с оговорками.

---

## 1. Упаковка на рабочей машине

```powershell
cd d:\__projects__\sfu-kaggle
powershell -ExecutionPolicy Bypass -File tools\pack_transfer.ps1
```

Скрипт делает четыре вещи.

| Шаг | Что происходит |
| --- | --- |
| Проверка состава | останавливается, если набор данных или веса неполны |
| Пароль доступа | создаёт `docker\.env` со случайным паролем, если его ещё нет |
| Упаковка | складывает всё в один архив рядом с папкой репозитория |
| Контрольная сумма | пишет файл `.sha256` для проверки после переноса |

Сжатие отключено намеренно. Кадры набора данных уже хранятся в сжатом виде, веса моделей сжимаются плохо, а проход по 4 ГБ занимает десятки минут без ощутимого выигрыша.

В конце скрипт печатает путь к архиву и пароль доступа. Пароль нужен, чтобы открыть ноутбук в браузере. Запишите его.

Полезные ключи:

| Ключ | Действие |
| --- | --- |
| `-OutDir E:\` | положить архив в другое место |
| `-Token мой-пароль` | задать пароль вручную, а не случайный |
| `-NoData`, `-NoModels` | собрать архив без данных или без весов |
| `-NoChecksum` | пропустить подсчёт контрольной суммы |

---

## 2. Перенос

Любым способом: съёмный диск, общая папка, копирование по сети. Переносятся два файла, архив и контрольная сумма к нему.

```powershell
scp d:\__projects__\sfu-kaggle-20260819.zip dmd@192.168.52.118:/home/dmd/
scp d:\__projects__\sfu-kaggle-20260819.zip.sha256 dmd@192.168.52.118:/home/dmd/
```

---

## 3. Подъём на целевой машине

Зайти на машину и распаковать.

```bash
cd ~
sha256sum -c sfu-kaggle-20260819.zip.sha256
unzip -q sfu-kaggle-20260819.zip
cd sfu-kaggle
```

Проверка контрольной суммы обязательна. Архив весит больше 4 ГБ, и обрыв при копировании даёт файл, который распаковывается частично и молча.

Дальше один вызов.

```bash
bash tools/start_stand.sh
```

Скрипт проверяет условия, собирает образ и поднимает ноутбук. Первая сборка идёт долго: загружаются системные пакеты и библиотеки расчётов. Повторные запуски используют готовый образ и занимают секунды.

Если ускоритель контейнерам недоступен, скрипт скажет об этом и спросит, продолжать ли. Без ускорителя стенд запустится, но одна ячейка будет считаться минутами вместо секунд. Для занятия это непригодно.

В конце скрипт печатает ссылку вида:

```
http://192.168.52.118:8888/lab?token=<пароль>
```

## 3.1. Особенность целевой машины

Машина 118 работает под RedOS. Доступ контейнеров к ускорителю настроен там особым образом, и это влияет на запуск.

В файле `/etc/nvidia-container-runtime/config.toml` на машине выставлено `no-cgroups = true`. При такой настройке обычный запрос ускорителя проходит, но прав на устройства контейнер не получает и ускорителя не видит. Снаружи всё выглядит рабочим: ноутбук открывается, ячейки выполняются, только расчёт идёт на процессоре.

Лечится это двумя строками в описании контейнера, они уже прописаны:

| Строка | Что даёт |
| --- | --- |
| `privileged: true` | полные права на устройства машины |
| `runtime: nvidia` | подключение библиотек ускорителя внутрь контейнера |

Тот же приём применён в рабочем развёртывании соседнего сервиса на этой же машине, поэтому он проверен на практике.

Если полные права нежелательны, в файле есть закомментированная замена: перечисление устройств `/dev/nvidia0`, `/dev/nvidiactl` и `/dev/nvidia-uvm` напрямую.

Возможна и третья помеха. RedOS использует принудительный контроль доступа, и он способен закрыть устройства даже при полных правах. Проверяется командой `getenforce`, снимается на время занятия командой `sudo setenforce 0`.

## 4. Проверка перед занятием

Открыть ссылку в браузере, открыть `notebooks/1_chto-vidit-mashina.ipynb` и выполнить ноутбук целиком, сверху вниз.

| Что смотреть | Признак нормы |
| --- | --- |
| Первая ячейка | выводит сводку по пяти камерам, отрабатывает без ошибки |
| Ячейка первого запуска | считает около двадцати секунд, а не минуты |
| Ролики | воспроизводятся прямо в выводе ячейки |
| Ячейка сохранения результата | создаёт файл рядом с ноутбуком |

Расчёт минутами вместо секунд означает одно: расчёт ушёл на процессор, ускоритель контейнеру не отдан. Проверяется это прямо, не дожидаясь занятия:

```bash
docker exec sfu-cv-stand nvidia-smi
docker exec sfu-cv-stand python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

Первая команда должна показать таблицу с моделью ускорителя, вторая — `True` и его название. Пустой вывод или ошибка означают, что ускоритель до контейнера не дошёл. Порядок действий в разделе 3.1.

Прогон стоит сделать заранее, до прихода участников. Первый вызов модели тратит около трёх секунд на её загрузку, и лучше, чтобы это время было потрачено до занятия.

## 5. Повседневные команды

Выполняются из папки `sfu-kaggle` на целевой машине.

| Задача | Команда |
| --- | --- |
| Посмотреть журнал | `docker compose -f docker/compose.yaml logs -f stand` |
| Остановить | `docker compose -f docker/compose.yaml down` |
| Запустить снова | `docker compose -f docker/compose.yaml up -d` |
| Пересобрать после правки зависимостей | `docker compose -f docker/compose.yaml up -d --build` |
| Узнать пароль доступа | `grep JUPYTER_TOKEN docker/.env` |

Правки кода в папке `stand` и ноутбука подхватываются без пересборки: обе папки подключены к контейнеру напрямую. Пересборка нужна только при изменении списка зависимостей.

## 6. Несколько участников одновременно

Стенд рассчитан на то, что каждый участник работает в своей копии ноутбука. Копия делается прямо в браузере, к имени добавляется суффикс: `1_chto-vidit-mashina-ivanov.ipynb`.

Каждая копия получает собственное вычислительное ядро: отдельный процесс, свои переменные, свой отрезок и свой результат. Открывать одну и ту же копию вдвоём нельзя, они попадут в одно ядро и будут перебивать друг другу переменные.

Ролики и файл результата разделяются по имени ноутбука сами. Ролики складываются в `notebooks/video/<имя ноутбука>`, файл показателей называется `результат-<имя ноутбука>.csv`. Участник для этого ничего не задаёт. Если имя определить не удалось, всё уходит в папку `общий`, и тогда разделение задаётся вручную вызовом `session.set_name`.

### Сколько человек влезает

Ограничение одно: память ускорителя. Каждое ядро держит свою копию моделей, и память освобождается только при перезапуске ядра, а не по окончании расчёта.

Замерено на RTX 3090, полный проход ноутбука:

| Этап | Занято памяти |
| --- | --- |
| Модель сегментации загружена | 1,67 ГБ |
| Первый расчёт по текстовому запросу | 3,78 ГБ |
| Добавлены модели глубины и сравнения изображений | 3,81 ГБ |
| Расчёт по пяти камерам, самая тяжёлая ячейка | 4,77 ГБ |

Расход на одного участника составляет 4,8 ГБ. На ускорителе с 24 ГБ помещается пять ядер вплотную, поэтому рабочее число — четыре участника одновременно, с запасом на пики.

Ускоритель при этом один. Четверо, нажавших расчёт в одну секунду, встанут в очередь, и вместо двадцати секунд каждый будет ждать около полутора минут. Ошибки не возникнет, но участник решит, что стенд завис. Ведущему стоит разводить группы по времени, а не запускать всех разом.

Свободную память видно из ноутбука вызовом `run.gpu_report()`.

Число участников для машины 118 нужно пересчитать под её ускоритель: замер выше сделан на 3090.

## Если что-то не запускается

| Симптом | Причина | Что делать |
| --- | --- | --- |
| `docker: command not found` | среда контейнеров не установлена | поставить её и повторить |
| Скрипт сообщает, что ускоритель недоступен | не установлен пакет доступа к ускорителю | поставить `nvidia-container-toolkit`, перезапустить службу |
| `bad interpreter` при запуске скрипта | переносы строк Windows | `sed -i 's/\r$//' tools/start_stand.sh` |
| Ячейка считает минутами | расчёт идёт на процессоре | проверить ускоритель командами из раздела 4 |
| Ноутбук открылся, но ускоритель внутри не виден | на машине выставлено `no-cgroups = true` | строки `privileged` и `runtime` в описании контейнера, раздел 3.1 |
| Ускоритель не виден и с полными правами | принудительный контроль доступа RedOS | `getenforce`, при `Enforcing` выполнить `sudo setenforce 0` |
| `unknown or invalid runtime name: nvidia` | на машине не зарегистрирован доступ к ускорителю | поставить `nvidia-container-toolkit`, прописать путь в `/etc/docker/daemon.json`, перезапустить службу |
| Страница не открывается снаружи | порт закрыт межсетевым экраном | открыть порт 8888 либо ходить по туннелю |
| `задайте токен в .env` при запуске | файл `docker/.env` отсутствует или пуст | создать его заново, скрипт делает это сам |
| Ноутбук просит пароль | ссылка открыта без него | взять пароль из `docker/.env` |
| Не хватает памяти ускорителя | несколько прогонов подряд | перезапустить вычислительное ядро в меню ноутбука |

## Оговорки

Порядок пройден не целиком. Образ на целевой машине собрался, ноутбук открылся на порту 8888. Расчёт на ускорителе внутри контейнера на момент написания не подтверждён, и до такого подтверждения стенд рабочим считать нельзя.

Настройки доступа к ускорителю взяты из рабочего развёртывания соседнего сервиса на той же машине, а не проверены на этом стенде. Обоснование в разделе 3.1.

Сборка образа требует интернета на целевой машине. Первый раз он там был. Если в следующий раз его не окажется, порядок меняется: образ собирается на рабочей машине, выгружается командой `docker save`, переносится отдельным файлом и загружается командой `docker load`. Файл выйдет тяжелее самого архива: образ весит 17,8 ГБ, и сжатие даёт мало, потому что основной объём в нём приходится на библиотеки расчётов.

Есть скрытая зависимость от сети при первом расчёте. Вспомогательный пакет ускоренных операций подгружает готовые сборки из внешнего хранилища при первом обращении к модели сегментации. Проверено замером на рабочей машине: под Windows подходящей сборки нет вовсе, и в журнале появляется предупреждение о пропуске трёх шагов обработки контуров. Для сочетания, которое собрано в образе, сборка существует, и на целевой машине она будет скачана при первом расчёте. Без интернета произойдёт тот же пропуск: контуры объектов станут менее аккуратными, сообщение об этом появится в выводе ячейки, расчёт при этом не прервётся.

Число участников посчитано для ускорителя рабочей машины. Для машины 118 его нужно пересчитать, разделив объём её памяти на 4,8 ГБ.

Ролики в папке `notebooks/video` перенесены готовыми. Ноутбук пересоздаёт их при выполнении, так что расхождение с настройками занятия исключено.

Пароль доступа лежит в открытом виде в файле `docker/.env` внутри архива. Для стенда в локальной сети этого достаточно. При переносе через посторонний носитель пароль следует сменить после распаковки.
